## 4. Giải thích phần kỹ thuật đã thực hiện

### Vấn đề cần giải quyết

- **Ingestion**: Lấy dữ liệu bài báo từ API Crossref về hệ thống nội bộ nhưng đảm bảo không bị gián đoạn (offline) khi API lỗi. Đồng thời chuẩn hóa thô JSON thành các cấu trúc class.
- **Cleaning**: Các metadata (ngày tháng, text summary) chứa HTML rác, múi giờ khác nhau. Cần làm sạch, lọc trùng lặp và tính `age_days` (độ tuổi dữ liệu) để sau này phục vụ cho việc đánh giá Freshness.

### Cách triển khai

1. **Ingestion (`crossref.py`)**: 
   - Hàm `fetch_source_records` sử dụng Dual-mode. Cố gắng lấy qua API (với timeout). Nếu có lỗi mạng hoặc API HTTP 429, thì catch exception và nạp file từ snapshot (fallback mode).
   - Hàm `parse_crossref_payload` duyệt từng kết quả. Dùng regex `re.sub(r'<[^>]+>', '', raw_summary)` để xóa HTML. Parse cấu trúc mảng lồng ghép `date-parts` thành string ISO-8601.
2. **Cleaning (`cleaning.py`)**:
   - Khởi tạo DataFrame từ list records (`asdict`). Đảm bảo `published` và `run_date` về cùng một múi giờ (UTC) bằng `.dt.tz_localize("UTC")` và `.dt.tz_convert("UTC")` trước khi trừ nhau lấy `.dt.days`.
   - Kết hợp các trường cần thiết vào cột `text_for_embedding`. Khử các dòng rỗng (title, summary) và `.drop_duplicates(subset=["paper_id"])`.

## 5. Một quyết định kỹ thuật quan trọng

- **Bối cảnh:** Xử lý ngoại lệ cho phần lấy dữ liệu từ Crossref API.
- **Các phương án đã cân nhắc:** 1) Retry exponential backoff. 2) Fallback về đọc file snapshot tĩnh có sẵn (Dual-Mode).
- **Phương án đã chọn:** Phương án 2 (Fallback snapshot).
- **Lý do:** Trade-off về tính sẵn sàng và tốc độ học tập: vì API Crossref có thể limit request (HTTP 429) kéo dài do nhiều sinh viên cùng gửi request, việc dùng snapshot sẽ giúp pipeline vẫn có dữ liệu để chạy flow RAG và đánh giá quality downstream thay vì bị crash.
- **Bằng chứng quyết định phù hợp:** Pipeline chạy không bị dừng khi tắt Internet, code vẫn fetch thành công từ `data/raw/crossref_response.json`.

## 6. Một lỗi hoặc blocker đã xử lý

- **Triệu chứng/lỗi nguyên văn:** `NameError: name 'dataclass' is not defined. Did you mean: 'dataclasses'?`
- **Lệnh hoặc bước tái hiện:** Chạy test script cho `fetch_source_records`.
- **Nguyên nhân gốc:** Quên chưa import trực tiếp object `dataclass` từ thư viện `dataclasses` mà chỉ import toàn bộ module `dataclasses` (và đã đổi sang decorator `@dataclass(frozen=True)`). Ngoài ra còn dính lỗi `dataclasses.asdict` chưa sửa.
- **Cách xử lý:** Thay bằng `from dataclasses import dataclass, asdict` tại đầu các file `crossref.py` và `cleaning.py`. Sửa các hàm gọi tương ứng.
- **Cách xác minh sau khi sửa:** Chạy lại script python -c thành công (exit code 0).
- **Điều học được:** Khi refactor code hoặc gộp thư viện Python cần chú ý cả các decorator và object reference được sử dụng trong hàm.

## 7. Hiểu biết về luồng end-to-end

Giải thích ngắn gọn bằng lời của bạn:

1. Dữ liệu đi từ Crossref đến vector index như thế nào?
Dữ liệu được query từ API Crossref (hoặc fallback file raw JSON) qua Ingestion Module. Dữ liệu này được làm sạch, định dạng ngày giờ (Cleaning Module) và tạo chuỗi text tổng hợp. Sau đó, chuỗi văn bản được đưa qua model nhúng (Embedding) để sinh vector số học và đẩy (upsert) vào Vector Database (ChromaDB).
2. Evaluation set và ground-truth document IDs dùng để đo retrieval/answer quality ra sao?
Evaluation set (chứa câu hỏi mẫu) được Agent truy vấn. Hệ thống so sánh document được agent (retrieval) trả về với ground-truth document ID (tài liệu thực tế chứa đáp án đúng) để tính hit rate/f1 token. So sánh câu trả lời của agent với câu trả lời chuẩn (judge score) để đo chất lượng trả lời.
3. Quality checks khác freshness monitoring ở điểm nào trong bài lab?
Quality check (dùng Great Expectations) đảm bảo tính toàn vẹn của dữ liệu (schema, non-null, deduplication). Freshness monitoring tập trung vào tính 'thời sự' của thông tin: theo dõi cột `age_days` (khoảng cách ngày chạy so với ngày xuất bản) có vượt ngưỡng cho phép hay không.
4. Vì sao phải dùng cùng test set cho baseline, corrupted và repaired?
Để đảm bảo điều kiện đánh giá là đồng nhất (cùng một tập câu hỏi). Bất kỳ sự suy giảm hoặc phục hồi nào trong các metric (hit rate, accuracy) sẽ trực tiếp phản ánh chất lượng hệ thống ứng với trạng thái dữ liệu thay vì do độ khó câu hỏi thay đổi.
5. Repair được xem là thành công dựa trên artifact và metric nào?
Thành công khi Quality Report và Freshness Report pass tất cả các rule. Metric (VD: `retrieval_hit_rate` và `judge_accuracy`) quay trở lại tiệm cận hoặc bằng với mức của tập Baseline ban đầu.

## 8. Phân tích kết quả

### Metrics chính

| Metric/signal          | Baseline | Corrupted | Repaired | Nhận xét của cá nhân |
| ---------------------- | -------: | --------: | -------: | ------------------------- |
| `retrieval_hit_rate` |      1.0 |       0.6 |      1.0 | Giảm mạnh khi bị lỗi, phục hồi hoàn toàn sau repair |
| `mean_token_f1`      |      0.8 |       0.3 |      0.8 | Rớt thê thảm do lấy sai context |
| `judge_accuracy`     |      0.8 |       0.4 |      0.8 | Suy giảm tỷ lệ thuận với Hit Rate |
| `mean_judge_score`   |      4.2 |       2.6 |      4.2 | Hallucinate khiến câu trả lời kém chất lượng |
| Quality checks         |      Pass |       Fail |      Pass | Cổng GX bắt được lỗi Duplicate |
| Freshness status       |      Pass |       Fail |      Pass | Phát hiện được data bị quá hạn |

### Kết luận từ số liệu

Hoàn thành hai chuỗi nguyên nhân–bằng chứng sau:

1. Data corruption → Các bản ghi bị nhân bản (duplicate) hoặc timestamp bị set lùi lại xa → Agent metric như hit rate suy giảm vì retriever lấy phải văn bản lỗi hoặc dữ liệu cũ out-of-date.
2. Repair action → Cột trùng lặp được xoá bằng `.drop_duplicates(subset=["paper_id"])`, chuẩn hóa timezone → Hit rate / accuracy phục hồi như lúc đầu do Vector DB được dọn dẹp sạch.

Corruption nào ảnh hưởng rõ nhất và vì sao?
Việc mất tính freshness (bị thay đổi năm published thành quá cũ) hoặc duplicate bản ghi. Agent sẽ hallucinate vì sử dụng kiến thức lạc hậu không còn đúng tại thời điểm câu hỏi yêu cầu. Duplicate làm chật kết quả top-k, cản trở văn bản đúng lọt vào context.

Kết quả nào khác với kỳ vọng ban đầu?
Không có kết quả nào đi ngược lại với kỳ vọng. Các chỉ số đều giảm đúng như dự đoán (Hit Rate rớt mạnh) khi tập dữ liệu bị làm bẩn, chứng minh được vai trò sống còn của Data Quality trong RAG.

## 9. Điều học được và hướng cải thiện

### Ba điều quan trọng nhất

1. Việc phòng thủ (fallback offline) trong pipeline data là rất quan trọng để hệ thống Data/AI không gãy hoàn toàn khi API third-party gặp sự cố.
2. Xử lý timezone đồng nhất (ép về UTC) là bước tối quan trọng để không dính lỗi offset khi tính `age_days` hoặc so sánh thời gian.
3. Không thể chỉ nhìn vào số lượng record thành công; nội dung bên trong như duplicate hay rác HTML có thể thầm lặng giết chết performance của RAG (Silent Failure).

### Nếu có thêm thời gian

Tôi sẽ implement thêm logic check checksum hoặc schema validate (pydantic) ngay trong bước Ingestion thay vì để đến Quality check downstream, giúp loại bỏ record xấu ngay từ API endpoint (Fail fast).
